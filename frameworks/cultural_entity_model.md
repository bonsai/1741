# 文化エコシステムのエンティティモデル

## 目的

民謡・民舞・祭り・イベント・団体・実行委員会・自治体・個人等を、それぞれ独立したIDで管理し、多対多の関係を記録する。特定の自治体や団体を文化資源の親・所有者として固定しない。

初期の調査・記述はMarkdownを正本として行い、構造が安定した段階でJSONL・Schemaへ移行する。

## 1. エンティティ種別

| エンティティ | ID接頭辞例 | 説明 |
|---|---|---|
| 文化資源・曲 | `cr-` | 民謡、新民謡、Neo民謡、民舞、芸能、祭り等 |
| 団体・組織 | `org-` | 保存会、民踊会、NPO、企業、学校、観光協会等 |
| 実行委員会 | `com-` | イベント等の企画・運営を担う委員会 |
| イベント | `evt-` | 祭り、公演、発表会、コンテスト、ワークショップ等 |
| 自治体 | `mun-` | 都道府県、市町村、特別区等。自治体マスターの正式IDと対応させる |
| 個人 | `per-` | 作者、伝承者、演者、研究者等。公開・個人情報方針に従う |
| 場所・施設 | `plc-` | 会場、記念碑、文化施設、伝承地等 |
| 活動 | `act-` | 稽古、記録、教育、保存、助成、広報等の継続的・個別活動 |

接頭辞は識別の補助であり、ID自体は不変とする。名称変更・統廃合・改称があっても既存IDを使い回さない。

## 2. 多対多の関係

- ひとつの団体が複数の曲・芸能を継承・演奏する。
- ひとつの曲・芸能に複数の団体・個人が関わる。
- ひとつのイベントに複数の曲・芸能・団体・出演者が参加する。
- ひとつの実行委員会が複数のイベントを企画・運営する。
- ひとつのイベントを複数の自治体・企業・団体が支援する。
- ひとつの曲が複数の自治体・地域に伝承・普及する。

関係は「親子」だけで表現せず、役割・期間・根拠を持つ独立した関係レコードとして扱う。

## 3. イベントと活動の区別

**イベント（evt）** は開催日時・会場・主催者・出演者・プログラム等を持つ開催単位。例：年次の祭り、特定年の総おどり、公演、発表会。

**活動（act）** は保存・継承・教育・記録・助成・広報などの実施内容。イベント形式をとる場合もあるが、イベントそのものと同一視しない。

同じ祭りの毎年の開催は、継続するイベントシリーズ（シリーズID）と各開催回（個別event_id）を分ける。名称が同じでも開催年・会場・主催体制が違えば別の開催レコードを作る。

## 4. 実行委員会と団体

実行委員会は独立した組織エンティティとしてIDを付与する。構成団体・事務局・委員長・協賛者・後援者は別エンティティとして保持し、委員会との関係に役割と任期・期間を記録する。

一つの委員会が複数イベントを担当する場合、委員会IDを共通にして各イベントから参照する。年度ごとに組織構成が変わる場合は、構成員の関係期間を更新・追加し、過去の履歴を消さない。

## 5. 新民謡・Neo民謡の分類

「民謡」という語を単一の年代・真正性で定義せず、作品の成立背景・創作性・伝承・再創造を複数の属性で記録する。

推奨する分類候補：

- **伝統民謡**：地域社会で伝承されてきた歌・旋律・歌唱慣行。成立時期不詳もあり得る。
- **新民謡**：近代以降、地域振興・観光・舞踊・レコード等との関係で新たに創作・普及した地域歌曲。個別作品の自己称・研究上の定義を出典付きで記録する。
- **創作民謡**：作者・作詞作曲・制作時期が確認できる、民謡様式・地域性を意識した創作。
- **Neo民謡**：現代の音楽・舞踊・メディア・テクノロジー等を通じた再解釈・再構成・新作。プロジェクト独自の編集分類として運用し、学術的に確立した分類と誤認させない。
- **民謡由来の翻案・リミックス**：既存曲をもとに歌詞・編曲・振付・言語・表現を変更した派生作品。

複数属性を許容する。作品の分類を固定的な優劣や伝統性のランキングに使わない。原曲と翻案作品は別IDにし、`derived_from` 等の関係で接続する。

## 6. IDとフォルダ規約

各エンティティはIDごとにフォルダを持つ。

```text
records/
  cultural-resources/{resource_id}/
  organizations/{organization_id}/
  committees/{committee_id}/
  events/{event_id}/
  municipalities/{municipality_id}/
  people/{person_id}/
  places/{place_id}/
  activities/{activity_id}/
```

各フォルダはまず `README.md` を必須とし、調査が進んだら `survey.md`、`history.md`、`sources.md`、`members.md`、`program.md` 等を追加する。空のファイルを先に大量生成しない。

## 7. 可視化を前提にした記述

各Markdownの冒頭に、少なくとも次を記載する。

- `record_id`
- `entity_type`
- `name`
- `record_status`
- `source_status`
- `related_ids`

本文の関係一覧には、相手のID・名称・関係役割・期間・根拠を記載する。これによりMarkdownからノード・エッジを抽出し、ネットワーク図、年表、地図、イベント参加関係図を生成できる。

## 8. 可視化の種類

1. **文化資源ネットワーク**：曲・団体・個人・自治体・イベントの接続。
2. **団体ポートフォリオ**：一つの団体が関わる複数の曲・活動・イベント。
3. **イベント構成図**：実行委員会、主催、共催、後援、出演、プログラム、会場。
4. **伝承地マップ**：発祥・伝承・普及・開催地を区別した地理表示。
5. **系譜・派生図**：原曲、新民謡、翻案、Neo民謡の派生関係。
6. **時間軸**：作品成立、団体設立、イベント開催、担い手交代、活動履歴。

可視化は確認済みの関係と未確認の仮説を区別して表示する。線の太さやノードの大きさを、根拠のない文化的価値の大小として表現しない。

## 9. おてもやんへの適用

おてもやんは独立した文化資源IDを維持する。熊本県・熊本市は別の自治体ID、熊本民踊会等の団体は組織ID、火の国まつりはイベントシリーズまたはイベントID、おてもやん総おどりの各開催回は開催年ごとのイベントIDとして調査する。

実行委員会の正式名称・組織実態・開催回ごとの体制を確認してからIDを確定する。現時点で未確認の委員会名や組織IDを推測で作らない。

## 10. データ品質原則

- 一次資料・公式資料・研究資料・報道・聞き取りを区別する。
- 同名の団体・イベントを名称だけで統合しない。
- 組織の改称・統合・解散は履歴として保持する。
- 役割（主催・共催・主管・協賛・後援・出演・参加）を混同しない。
- 不明な関係は仮説・要確認とし、確定データに混ぜない。
- IDを振ることと、実在・関係を確認したことを混同しない。
